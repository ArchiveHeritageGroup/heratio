# v1.154.670 (2026-08-25)

docs: track the credential-phishing incident response write-up, which existed only as an untracked file on the demo instance. Found during the v1.154.669 deploy: docs/reference/credential-phishing-incident-response.md had been written straight onto /usr/share/nginx/heratio on 2026-08-24 at 15:45 and existed nowhere else - not in git, not on dev. It is written as a repeatable procedure rather than a one-off note, and a host rebuild or a demo restore would have taken it with nothing to notice. Copied verbatim; checked for credentials before committing and it carries none. It also answers a question left open on #1485. The mailbox OAuth grant was revoked at 15:20:47 that afternoon, blinding both deploy gates, and the cause was recorded as unknown because Azure only reports that a password was changed or reset. This is why: a staff member entered Microsoft credentials into a phishing page reached through a live business thread, and the reset was deliberate incident response. Sign-in logs confirmed the credentials were never used. Not a mystery and not a fault - the right action, which happened to break a check added the same day. WHAT THE DOCUMENT IS WORTH KEEPING FOR is the order of operations: revoke sessions BEFORE rotating the password, because a real-time phishing proxy captures the session cookie Microsoft issues back and that cookie does not care that the password later changed. Then authentication methods, because registering an authenticator is the first persistence move and a planted temporaryAccessPass is a password-equivalent bypass that will not appear if only push MFA is examined. Then mailbox rules and forwarding, then OAuth consents - the one thing session revocation does not touch, since an app holding offline_access carries its own refresh token - and only then the sign-in logs. It also records the traps: an empty Search-UnifiedAuditLog result reads as an all-clear when UnifiedAuditLogIngestionEnabled is false, and a v4-only hosts sinkhole leaves AAAA resolution untouched on a Cloudflare-fronted domain. ONE OBSERVATION IT MAKES INDEPENDENTLY, and which this repo has now hit twice in two days: the nginx bot blocker maps $http_user_agent on INBOUND requests, so adding a domain your staff visit outbound produces 'a control that looks real and does nothing, which is worse than not adding it'. That is the same finding as #1484, where facet-crawl-guard was included in the Heratio vhosts and could not match a single request. Two independent routes to the same conclusion in the same week is worth noticing. The untracked copy is removed from the demo instance now that the file is in git, so the next deploy can place the tracked version without a checkout conflict.
