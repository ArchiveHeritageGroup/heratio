# v1.154.627 (2026-08-17)

fix(deploy): pre-deploy DB backup used the app's password with -u root, so sasa deployed with NO restore point. The dump exported MYSQL_PWD from the instance's .env but connected as root; that only worked on heratio.org because its app happens to run as the root DB user. On sasa (DB user 'sasa') the user and password disagreed, mysqldump failed with 'Access denied for user root@localhost (using password: YES)' on both attempts, and the deploy printed a WARN and carried straight on - found immediately after deploying v1.154.626, whose sasa backup directory was created but left empty. Now dumps as that instance's own DB_USERNAME (defaulting to root) with --no-tablespaces, since dumping tablespace info needs the PROCESS privilege an app user lacks and its absence printed an access-denied line while still exiting 0. Also: a dump is now only accepted if it ends with mysqldump's 'Dump completed' marker, because a truncated or refused dump still leaves a plausible-looking .gz; and a failed backup now ABORTS the deploy (exit 1) instead of continuing, with --no-backup to override knowingly - proceeding without a restore point is how a bad migration becomes unrecoverable. Verified: both instances dump completely with their own credentials (sasa 17M as 'sasa', heratio 31M as 'root'), abort path exits 1 before touching git, --no-backup continues; sasa's missing v626 restore point has been taken by hand
