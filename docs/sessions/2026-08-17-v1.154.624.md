# v1.154.624 (2026-08-17)

fix(#1470): rehome every remaining status row onto its own QubitStatus object. The orphan backfill in v1.154.623 fixed the rows pointing at nothing; verifying it showed the wider column was worse - status.id was never meaningful (it equalled object_id in 1 row of 9906) and most values were ids from status's own AUTO_INCREMENT counter that happened to COLLIDE with real object rows of other kinds: information objects, terms, digital objects. On dev that was 9621 rows resolving to an unrelated entity against 285 correct, so a join on status.id succeeded and returned nonsense - worse than resolving to nothing, because nothing is detectable and wrong-but-present is not. Every remaining row now has its own freshly allocated QubitStatus object. Verified on dev: 9621 moved, 0 skipped, 9906/9906 now on a QubitStatus row, row count unchanged, the CRC32 checksum over every (object_id, type_id, status_id) tuple byte-identical, object grew by exactly 9621, and every CTI child (information_object, term, digital_object, actor, repository) still has its own object row - nothing was displaced from the ids the status rows vacated. Batched 200 rows per transaction; 10 seconds for 9621. Idempotent. With the column finally meaning one thing, an FK from status.id to object.id would now be worth adding - though it still could not enforce class_name, which is the part that actually matters
