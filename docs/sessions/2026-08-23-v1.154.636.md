# v1.154.636 (2026-08-23)

chore(tools): commit the Blade always-fallback binding scanner and its baseline - #1478. Three defects of one shape turned up by accident in two days: a view reads $row->prop with a ?? fallback, the query behind that row never produces prop, and the fallback fires on every row of every page load. Nothing errors. #1477 was the loan-rules screen reporting '14 days / 5 max items' for every rule; the checkout preview was about to become the second; the third was the overdue list, which had shown a BLANK PATRON, 0 DAYS OVERDUE and 0.00 FINE on every row for as long as the screen has existed, surviving because two of its five columns worked and the table looked alive. The ?? is what lets these live - without it they would be Undefined property warnings and would have been fixed years ago. tools/scan-blade-bindings.php makes the hunt reproducible instead of a one-off shell command. WHAT IT COUNTS: not a single unresolvable property but a whole ?? chain in which NO alternative resolves. That distinction came from the data, not from theory - $s->area_sqm ?? $s->floor_area WORKS because the real column is named first and the stale alternative never runs, whereas $s->ceiling_height ?? $s->height renders a permanent blank because the column is height_m and both are wrong. Those two-name chains are the fingerprint of a column rename that was only half finished, and are exactly what hid the unfinished half. Baseline records 131 unique (file, chain) findings across 73 views. NOTE that is a correction to the 167 quoted when #1478 was filed: 167 counted repeated occurrences, 131 counts unique pairs, which is the better measure because it is one defect to fix. Identifier sweep reads 66,309 names against the earlier run's 70,688 over an identical 2,668 source files - verified directly - because PCRE's \w is ASCII while Python's is Unicode-aware, so the earlier figure counted accented words from comments; irrelevant here and the ASCII behaviour is the more correct. Producibility is judged generously on purpose: a property counts as real if it names a column anywhere in the schema (5,525) or appears in any non-Blade source, which lets some real bugs through rather than crying wolf. The output is a work queue to triage, NOT 131 confirmed user-visible bugs - each needs checking against its actual query, as was done for the three fixed cases and for the gallery Spaces report, which permanently shows no wall length, no ceiling height and no venue for every space. --check compares against the baseline and exits 1 on anything new; VERIFIED by reintroducing the exact defect this started from (swapping the fixed $o->patron_name for $o->patron_name_xyz ?? $o->borrower_display), confirming the failure names the file and chain, then restoring and confirming it passes. It also reports findings that have disappeared so the baseline can only shrink. No database is a soft failure - it warns, skips the schema check and still runs the identifier sweep, keeping it usable in a bare checkout. Two bugs in my own first cut are fixed: '\t' in single quotes is not a tab in PHP, so the separator printed literally and the file-count dedup silently failed, reporting '131 chains in 131 files' when the truth was 73 - the same species of plausible-looking wrong value the tool exists to find. NOT wired into CI: adding a job to test.yml changes behaviour for every branch and is a separate decision. No application code is touched, so the test suites are unaffected.
