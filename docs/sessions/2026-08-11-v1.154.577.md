# v1.154.577 (2026-08-11)

fix(rights): #1464 Creative Commons AND rights statement never displayed on record pages + #1463 legacy URL redirects. DISPLAY BUG: the archival-description show page and the library show page both resolved extended_rights.rights_statement_id and .creative_commons_license_id against term_i18n, but neither is a taxonomy term - rights statements live in rights_statement/rights_statement_i18n and CC licences in rights_cc_license/rights_cc_license_i18n. The ids never matched, both names came back null, and because each row is wrapped in @if($extRsName)/@if($extCcName) the Rights statement and Creative Commons rows silently never rendered at all - no error, no empty label, just absent, which is why it went unreported. Proven on live data: extended_rights id=6 has cc_id=1 rs_id=1, which resolve to 'CC0 1.0 Universal (Public Domain)' and 'In Copyright' in the correct tables and to NULL in term_i18n. Both blades now query the right vocabularies (CC falls back to rights_cc_license.code when no i18n name exists). Note ExtendedRightsService and RightsHolderService already joined rights_cc_license correctly - only the two inline blade lookups were wrong, so the same column was being resolved three different ways. LEGACY URLS (#1463 follow-up): /right/add?slug= and /deaccession/add?accession= were the AtoM-era URLs the old buttons used and may still sit in bookmarks and saved links; they 404'd after the buttons were rewired. Added legacyRightAdd/legacyDeaccessionAdd which 301 to the real accession rights / deaccession pages, or fall back to the accession browse with a note when the slug or id does not resolve. Not resurrected features - just so an old link redirects instead of dying. Verified: /egyptian-boat renders 200 with both Creative Commons and Rights statement now visible; four affected records render; legacy URLs 301 to the right targets and bad input falls back cleanly; Unit 21/21 and Feature 231 tests still green
