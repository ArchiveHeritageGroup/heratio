# v1.154.725 (2026-09-08)

fix(exhibition): the presence sweep no longer deadlocks against its own upsert. The walkthrough beats 2-3 times a second per visitor, and every beat swept the whole building for stale rows, so garbage-collection load grew with the square of the audience. On 7 Sep 2026 that deadlocked on heratio.org: SQLSTATE 40001, delete from ahg_exhibition_presence where building_id = benson and last_seen < .... The cause is lock ORDERING, not a bad plan - the upsert immediately above holds a row via uq_building_token and then wants the (building_id, last_seen) range, while a concurrent beat's delete holds that range and wants the row. Both indexes exist and are exactly right, on dev and on production; checked rather than assumed, because a missing index would have been the easier and wrong answer. THE SWEEP WAS NEVER LOAD-BEARING, which is what makes the fix safe: both queries below it already filter last_seen >= now-12s, so a stale row is invisible to a visitor whether or not it has been deleted. Its only job is to stop the table growing. It now runs on roughly one beat in twenty-five, which makes the collection rate broadly constant instead of scaling with the crowd - correct, because the reason to collect does not scale with the crowd either, and a single visitor still sweeps about every ten seconds. Deadlock and lock-wait are then swallowed BY NAME, 1213 and 1205, and nothing else is: a bare catch would hide a missing table or a permissions failure behind the same silence, and this table's own history is a concurrency bug found only because it threw loudly - the updateOrInsert 1062 that became the upsert. Losing a sweep costs nothing; the next beat collects. Verified on dev before and after: with a visitor who left 60 seconds ago, the row is present and the live visitor's peer list is still empty, which is the property a visitor could actually notice, and after 300 beats the row is gone. Four tests pin both promises separately - invisible at once, collected eventually - plus that a live co-visitor is still shown and that a row only five seconds old survives the sweep, so it cannot evict someone merely between beats. The one probabilistic assertion says so in its own docblock, with the odds. 1114 Package tests pass, up from 1110, and 286 Feature tests pass. Closes the last of the three errors standing open on heratio.org.
