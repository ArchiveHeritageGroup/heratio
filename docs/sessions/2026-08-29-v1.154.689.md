# v1.154.689 (2026-08-29)

fix(search): es-reindex silently built a dynamically-mapped index and dropped records - #1494. createIndexFromMapping copied number_of_shards, number_of_replicas and analysis from the source index but NOT its mapping.total_fields.limit. archive_qubitinformationobject flattens to 1479 fields and sets its own limit of 3000, so cloning it under the 1000-field default failed every time. The response was never inspected and 'Created {target} with mapping from {source}' printed unconditionally, so the failure was reported as success; the mapping step then 404'd on an index that did not exist, and Elasticsearch auto-created it from the first bulk write with DYNAMIC mapping - gis an object instead of a geo_point, workKey text instead of keyword, no analysers, 24 fields against the source's 55. Map search and FRBR work-set clustering both silently returned nothing rather than erroring. The limit now travels with the mapping, the response is checked, and a failed clone says so and still creates a plain index so explicit field types apply instead of being decided by whatever the first document looks like. bulkIndex counted rejected documents but never said why; it now names the first id and reason, which is how the second bug was found - the cloned mapping is dynamic:strict and the doc builder emits seven library fields none of which exist in it, so library records were rejected outright and absent from search. All seven are now mapped, identifiers and enumerated values as keyword and prose as text. A post-reindex check verifies gis and workKey carry the type their features depend on, because a wrongly typed field returns nothing rather than failing. Verified on dev: 9544 of 9544 indexed where it was 9536, all 8 rejected records present, exact-ISBN keyword match and a geo_bounding_box query both return hits, analysers present, 60 fields. 246 Feature tests pass. Released as 689 rather than 688: a concurrent release took that tag while its own version.json bump did not persist, so the file lagged the tag and the next patch computed a number already in use.
