# v1.154.639 (2026-08-23)

fix(gallery,museum): stop the catalogue forms discarding 30 CCO fields on save - #1478. The gallery and museum edit forms are built to Cataloguing Cultural Objects, every field carrying its own help text and CCO citation, and they read as a serious standards implementation. Thirty of those fields went NOWHERE: absent from museum_metadata, absent from both controllers' validators, and absent from the $metaFields whitelists in GalleryService and MuseumService. A cataloguer filled them in, pressed Save, and the values were discarded - nothing errored, nothing was logged, and the form came back empty next time, which reads as 'I must not have saved it' rather than 'the system dropped it'. Among them is dimensions_display, annotated in the markup as REQUIRED, CCO 6.1: a form that marks a field required and cannot store it. ROOT CAUSE was two hand-maintained copies of one list - both sector services write the same museum_metadata table and each carried its own inline whitelist, so there was no single place where 'the CCO fields' are named and adding one to a form failed loudly nowhere. New AhgCore\Support\CcoFields is that place: one list driving the save, the validation rules and the SELECT for both services, the same consolidation as the three divergent loan-rule lookups in v1.154.634. Column names match the form field names EXACTLY and deliberately - name divergence is the root cause of the whole #1478 class, and matching them is what lets tools/scan-blade-bindings.php prove they stay wired. That costs some near-duplication (attribution_qualifier beside an existing unused creator_qualifier, dimensions_display beside dimensions) and it is a deliberate trade: an extra column is recoverable and visible, whereas guessing a CCO mapping wrong and silently writing 'Gallery 3, Bay B' into current_location_repository would be a worse and much quieter failure. ONE OF THE THIRTY NEEDED NO COLUMN: alternate_titles was a plural - information_object_i18n.alternate_title already exists and is already saved, so CCO 3.2 has been broken by a single character. ROW-SIZE WALL: the first cut used VARCHAR and failed partway with 1118 Row size too large, because museum_metadata's existing VARCHAR definitions alone account for 63,964 of InnoDB's 65,535-byte limit - 98% full. All 19 new columns are TEXT (a ~20-byte pointer, payload off-page); none needs an index or length constraint so nothing is lost. up() also cleans up after that aborted run, converting the three columns it left as VARCHAR - but ONLY where the column holds no data at all, so a re-run can never discard catalogued values. Anyone extending this table should assume the next VARCHAR will not fit. Migration lives in database/migrations, NOT the package: ahg-museum has no migrations directory and no loadMigrationsFrom(), so one placed there would silently never run; add_icip_sensitivity_to_museum_metadata sits at app level for the same reason and is the precedent. Mirrored to a new database/core/05_museum_cco_fields.sql, guarded and idempotent, verified loading twice against heratio_test. VERIFIED end to end: saved dimensions_display, materials_display, creator_display, location_within_repository, iconography, condition_summary, height_value and width_value through GalleryService::update() and read every one back through getBySlug(); test values removed afterwards. The scanner drops 131 -> 101, exactly thirty fewer, and both edit views disappear from the baseline entirely - independent confirmation rather than my own assertion. NOTE getBySlug() first returned null and it was NOT a regression: the record carried publication status 159 (draft) and the query correctly hides drafts from an unauthenticated caller, which a CLI script always is. 440 tests pass.
