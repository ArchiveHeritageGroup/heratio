# v1.154.708 (2026-09-01)

docs(ops): end-to-end install and upgrade runbook. Written by reading bin/install, bin/release, heratio-deploy.sh, heratio-demo-{reset,snapshot}.sh, /etc/cron.d and the php-fpm drop-ins on the running host rather than from memory, and verified against it at v1.154.707. PART A covers a fresh install: the three scenarios, the fourteen idempotent stages of bin/install, and - stated first because it is the one that turns a good install into a confusing outage - the php-fpm ReadWritePaths drop-in that ProtectSystem=full makes mandatory, including why cron-driven artisan writes logs fine while web requests 500. PART B covers upgrades: release on dev, push with root key because dev cannot push, --check before every deploy, and the conditional steps the deploy does NOT do (help re-ingest, ES reindex, facet rebuild) plus the one that bites - anything changed AFTER a deploy is not in the baseline the deploy just took, so 02:00 discards it unless you re-stamp. PART C collects the landmines, each of which has cost real time: restart php-fpm rather than reload because opcache.validate_timestamps=0 means CLI checks pass against code the browser is not running; a new package autoload line does not travel because bin/release excludes composer.json from every commit, so the package ships its code, registers nothing and 404s with no error anywhere; per-instance files need skip-worktree or the deploy aborts, and clearing the diff silently unregisters a package; package migrations only run if the provider calls loadMigrationsFrom; a migration-created table referenced in a query breaks CI, which builds its test DB from database/core/*.sql. PART D is rollback and PART E a checklist. One correction to an earlier claim while verifying: pre-deploy-* dumps ARE pruned on the same 14-day window as heratio-demo-*, by the script that writes them - the backlog seen earlier was simply a window in which neither script had run, and today deploys took it from 140 files to 103.
