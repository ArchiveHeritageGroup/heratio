# v1.154.618 (2026-08-16)

fix(cron): second unattended night. The two highest-volume failures were NOT bugs - llm-health (75/91) and services-check (53) were correctly reporting a real overnight outage of the AI gateway, which returns 200 again now. Backups confirmed working for the first time: two dumps landed on heratio.org dated today, so the v1.154.615 credential fix holds. Real fixes: refresh-facet-cache's lock timeouts were never an overlap-with-itself problem - /etc/cron.d/ahg-facet-cache runs the same command at the same minute and does more (it loops the dam and heratio databases), so two independent schedulers collided every hour and withoutOverlapping could not see across them; the managed row now stands down where that cron file exists. preservation-replicate passed 0 as digital_object_id, a nullable FK with no row 0, so every replication event insert violated the constraint - logEvent now accepts null, which is what a package-level event means, and replication records cleanly. Four more commands defaulted to the 'atom' connection and were denied on sasa (authority-dedup-scan, dedupe-scan, export-bulk, heritage-build-graph), now routed through DiscoverySource. Disabled rather than faked: 3d-multiangle, ai-translate and preservation-package require a per-run argument with no batch mode; metadata-export and export-bulk-ead write to directories that exist on no instance; heritage-build-graph writes entity_id/repository_id/level_id/cached_at into heritage_entity_cache, which has none of them - it targets the wrong table, which is a design question, not a rename, so its join was corrected and the schedule stopped. NOTE the seed-versus-rows trap caught me a third time: v1.154.615 disabled 3d-multiangle and ai-translate in the seed only, and the stored rows kept running
