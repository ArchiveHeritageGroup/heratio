# v1.154.673 (2026-08-25)

feat(io-manage): wire display_as_compound end to end - the last item on #1481. 'View children as compound?' has been offered on the digital-object edit page since the AtoM port, reading $do->display_as_compound - a column digital_object does not have - and discarded on submit, because update() only ever saved media_type_id. So the control always rendered 'No', never remembered a choice, and nothing anywhere read it. Three views once offered it; two were deleted earlier in #1478 and this is the last. WIRED WHERE IT ACTUALLY CHANGES SOMETHING, which is why the issue deliberately left it alone rather than adding a column. #1481 is explicit that this field must CHANGE how child objects render and that storing it alone would recreate the 'a number nothing enforces' problem behind #1477. So the flag is read by InformationObjectController::show(), where it now decides whether the record presents its children as one compound object - the carousel strip built from descendant thumbnails - or leaves them to be reached individually. Measured on a real record: unset renders 10 child thumbnails, No renders 0, Yes renders 10 again. ABSENT DEFAULTS TO TRUE, and that is the safety property. Never-chosen is a distinct state from No, so every existing record keeps behaving exactly as it does today and only an explicit No turns the strip off. A default of false would have silently emptied the carousel on every record in the estate. STORED AS AtoM STORES IT: a property named displayAsCompoundObject, scoped digital_object, on the INFORMATION object rather than the digital object - it governs how that record presents its children, not a fact about one file. New AhgCore\\Support\\PropertyRow does the read and write. property is class-table-inherited exactly like status: an object row carrying the id, a property row keyed to it, and the value in property_i18n. Writers across this codebase each open-code that three-table dance, which is precisely how the id-allocation bug behind StatusRow happened, so this follows that precedent - one place that allocates the object row means no caller has to remember. It also keeps 'never set' distinct from 'set to no', which the flag depends on. Verified the round trip through the real controller: saving No then Yes reads back correctly and leaves ONE property row rather than accumulating duplicates. A WRINKLE WORTH RECORDING rather than fixing here: the control lives on the digital-object edit page and appears only when that digital object's record has children, so a parent record with children but no digital object of its own has no route to the setting at all. That is inherited from where AtoM puts the control; changing it means moving the field to the record edit form, which is a larger UI decision than this issue asks for. 231 Feature tests pass; the show page serves 200 after the change.
