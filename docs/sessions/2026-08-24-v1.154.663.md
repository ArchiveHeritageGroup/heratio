# v1.154.663 (2026-08-24)

fix(deploy,backup): database dumps were created world-readable on a host with ~10 non-root service accounts. 251 of 471 existing .sql.gz dumps under /mnt/nas/heratio and /var/backups/heratio-deploy were mode 0644 or 0664, including the demo baseline, which is a full dump of the live demo database. Verified concretely: an unprivileged local account could read the baseline, and it carries email_setting.smtp_password - a live Gmail app password - in plaintext. A dump contains everything the database contains, so the credential is only the sharpest example: user rows and session data travel in the same file. All 471 existing dumps are now 0600 and the baseline is no longer readable by a non-root user. THREE WRITERS FIXED AT SOURCE rather than by a chmod sweep that the next dump would undo: heratio-deploy.sh's pre-deploy _backup(), heratio-demo-snapshot.sh's baseline plus its dated copy, and /usr/local/bin/mysql_full_dump.sh's nightly --all-databases dump. Each now sets umask 077 for the dump window so the file is never briefly readable, rather than chmod-ing after the fact. Verified by running the real snapshot: the new baseline and its dated copy are both 0600 root:root. NOTE WHAT THIS IS NOT. It is not a credential rotation. The password is not in git, not in git history, not in any session log, and the install.sql seed carries an empty placeholder - so there is no evidence of exposure beyond this host, and rotating a working credential without suspected exposure is churn rather than hygiene. The defect was the file mode, and the file mode is what is fixed. /etc/msmtprc was already correctly 0640 root:www-data. TWO SELF-INFLICTED BUGS CAUGHT BEFORE SHIPPING, both a wrapper quietly changing a status its caller tests on. Wrapping mysql_full_dump.sh's pipeline in a subshell would have made RC=PIPESTATUS[0] on the next line read the subshell's status instead of mysqldump's, disabling both the retry and the too-small-file guard; umask is now set and restored around the unwrapped pipeline instead, proven in isolation to create 0600 while preserving PIPESTATUS. And _backup() ending on 'chmod || true' would have made it always report success - it now captures and re-returns the rc. Recorded because _backup already returned gzip's status rather than mysqldump's, which is safe only because _backup_ok validates the completion marker; that pre-existing behaviour is preserved deliberately rather than changed mid-fix. Both deploy/sbin scripts are drift-tracked exact, so both were reinstalled to /usr/local/sbin; check-config-drift reports no drift across 16 files.
