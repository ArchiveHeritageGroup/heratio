# v1.154.623 (2026-08-17)

fix(#1470): backfill status rows whose id belonged to no object. 275 rows on dev (417 on heratio.org) carried ids taken from status's own AUTO_INCREMENT counter, pointing at no object row at all. Each now gets a freshly allocated QubitStatus object row, with every other column untouched. Safe because status.id is referenced by nothing - no foreign key anywhere points at it, no code reads it (rows are always located by object_id + type_id), and there is no FK from status.id to object.id either, which is how the orphans arose unnoticed. Verified on dev: 275 rehomed, 0 skipped, 0 orphans left, row count unchanged at 9906, and the CRC32 checksum over every (object_id, type_id, status_id) tuple is byte-identical before and after - only the ids moved. Idempotent; a re-run finds nothing. IMPORTANT FINDING, NOT FIXED HERE: the wider column is worse than the orphans suggested. status.id equals object_id in just 1 of 9906 rows, so the value was never meaningful, and of the rest 9621 now resolve to a QubitStatus object while 9621 resolve to an UNRELATED entity - information objects, terms, digital objects - because an auto-assigned id happened to collide with a real object id. Only 285 follow the intended convention. A join on status.id therefore succeeds and returns nonsense, which is arguably worse than resolving to nothing. Rehoming all of them is a materially larger operation than this issue asked for and is left as a decision
