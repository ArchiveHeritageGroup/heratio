# v1.154.657 (2026-08-24)

fix(function-manage): five sections the function show page looped and never received - #1478. Parallel forms of the name, other forms, related authority records, and the language and script of the description were all present in the template and passed by nobody. Every one is isset()-guarded, so nothing ever threw: the sections simply did not render, on every function page, however much was recorded against them. That is the same defect class as the rest of #1478 and the scanner cannot see it - there is no ?? chain to flag, only a guard that is quietly false, which is why it survived the sweep that cleared the rest. PARALLEL AND OTHER FORMS both live in other_name and are told apart by their type term. The term is matched by NAME rather than id: a seeded taxonomy term gets whatever id the instance hands out, so a hardcoded 148 would be correct on exactly one installation - the lesson from the harris-matrix deposit/interface typing. Standardized form is deliberately NOT folded into other forms; it is an ISAAR element for authority records and not an ISDF element for functions, and showing it would put a value under a heading that does not describe it. Verified: a seeded standardized form appears in neither list. LANGUAGE AND SCRIPT come from the property table as the serialized array AtoM writes, decoded with allowed_classes=false because this is data and must never instantiate an object, then mapped through the canonical AhgCore LanguageOptions so a function page reads English and Afrikaans rather than en and af, and reads them the same way every other page does. An unrecognised code is passed through unchanged rather than dropped, because an unknown code is still information. RELATED AUTHORITY RECORDS are read from both directions of the relation table and merged, since nothing enforces which end a function-actor relation is recorded from. The class_name filter is QubitActor exactly and NOT the wider set of actor subclasses, even though repository, donor and rights-holder rows all live in the actor table: the view links each result to actor.show, and ActorService restricts that route to QubitActor. Verified live - /actor/ a repository slug returns 404 while /actor/ an actor slug returns 200 - so widening the filter would emit links straight to a 404, and QubitUser rows are login accounts that are not authority records at all. The relation description and its dates come through the same relationDatesExpression() added earlier in this issue. VERIFIED end to end against seeded data and then over HTTP, with every seeded row removed afterwards and the instance returned to its prior state. A note for the next person: the entire ISDF body of this page sits in the @else of a RiC view-mode switch, so a function whose stored view mode is ric renders none of it - I spent a while proving the sections were missing when the page was simply in the other mode. 225 Feature tests pass.
