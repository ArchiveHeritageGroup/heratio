# v1.154.638 (2026-08-23)

chore(ci,tools): gate new Blade always-fallback bindings, and triage the existing 131 - #1478. CI: tools/scan-blade-bindings.php --check now runs in the code-quality job. It does NOT fail on the existing 131 - fixing those is a separate project - only on something NEW, so the population cannot grow while triage proceeds and the baseline may only shrink. php -l cannot see this class of defect: a view reading $row->prop with a ?? fallback where the query never produces prop is valid PHP, so it never errors and the fallback simply fires on every row. TOOL: the scanner no longer touches a database. An earlier cut queried information_schema; running it BOTH ways over this repo gave an identical 131 across 73 files, because a column created by a migration is named as a PHP string ($table->string('foo')) and one created by an install.sql is named in the DDL, so the identifier sweep already had them. Dropping it removes a real failure mode as well as a dependency - the CI database is built from database/core/*.sql alone and carries far fewer tables than a full install, so a baseline recorded against a developer's database would have reported phantom regressions in CI. The scan is now repo-only, deterministic, and needs no database service in the workflow. TRIAGE (docs/reference/1478-blade-binding-triage.md, all 131 listed): 44 are NOT display bugs - they are form fields that discard input. Controls that render empty, are absent from the validator, and are dropped on submit; someone types, saves, and the data goes nowhere, with no error at any point. The other 87 are display-only. 30 of the 44 are the gallery and museum edit forms: GalleryController::edit() loads the artwork via GalleryService::getBySlug(), which selects information_object joined to museum_metadata, and twenty of the field names exist in NONE of museum_metadata's 90 columns nor anywhere in ahg-gallery/src or ahg-museum/src. Both forms are built around Cataloguing Cultural Objects elements with per-field help text and CCO citations - including dimensions_display, annotated in the markup as REQUIRED, CCO 6.1, which silently drops whatever is typed into it. A form that presents itself as standards-compliant, marks a field required, and cannot save it is the sharpest form of this defect. 3 more are researcher-type booking limits, truncated against the real columns: max_advance_days vs max_booking_days_advance, max_hours_per_day vs max_booking_hours_per_day, max_materials vs max_materials_per_booking - so those limits cannot be edited at all. NOTE how that one nearly escaped: a substring grep for max_materials hits max_materials_per_booking and looks like a match; the scanner tokenises on \w+ and compares whole identifiers, so it flagged it correctly - the same trap as the fixed-window audit heuristic that has bitten this repo before. Suggested order is the 30 CCO fields, then the 3 booking limits, then the remaining 11 class A, then class C prioritising anything rendering a NUMBER rather than a blank, because a wrong figure is trusted in a way an empty cell is not. NO FIXES APPLIED - triage only. Class A groups were each verified by hand against the actual query and save path; class C is not individually verified and the scanner's heuristic caveat still applies. Released as .638 after fast-forwarding onto a concurrent .637. No application code touched.
