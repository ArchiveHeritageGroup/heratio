# v1.154.581 (2026-08-12)

fix(icip): #1464 move 15 TK/BC label assignments onto the ICIP model - they were taking no part in community-protocol enforcement. There were THREE assignment tables and TWO vocabularies for the same thing: extended_rights_tk_label (15 rows, LIVE, keyed to extended_rights.id, vocabulary rights_tk_label with 19 labels coded TK-A), rights_object_tk_label (0 rows, keyed to object_id, community degraded to FREE TEXT), and icip_tk_label (0 rows, keyed to information_object_id, vocabulary icip_tk_label_type with 22 labels coded tk_a). THE DECIDING FACT: TermProtocolService (#1388/#1406) reads icip_tk_label and joins icip_tk_label_type.default_access_condition to drive community-protocol enforcement - so labels recorded anywhere else are display-only. The 15 live TK/BC labels applied across six records therefore took NO part in the protocol layer built to honour them: Indigenous and biocultural labels applied by an operator that the enforcement path could not see. icip_tk_label + icip_tk_label_type win on every axis: the enforcement path, the Local Contexts catalogue the Hub integration (#1448) binds to, and real provenance (community_id, applied_by, local_contexts_project_id) where rights_object_tk_label keeps only a free-text community name. Codes map by normalising TK-A -> tk_a; 14 of 15 mapped cleanly. The fifteenth, BC-CB 'BC Consent Before', had no counterpart and would have been dropped, so it is added to the catalogue preserving its Local Contexts URI and carrying its real name across from rights_tk_label_i18n rather than deriving one from the code. ITS ACCESS CONDITION IS A DELIBERATE NON-DECISION: default_access_condition is NOT NULL so it cannot be deferred in the data, and it is set to 'attribution', which is non-restricting (TermProtocolService::RESTRICTED is sacred_secret/restricted/gendered/seasonal/community_voice). That preserves exactly today's behaviour - nothing newly gated, nothing newly opened. A consent-required label arguably SHOULD be 'restricted', but that would newly gate three records, and how a cultural label governs access belongs to the archive and the source community, not to a data migration. FLAGGED FOR A DELIBERATE ANSWER. Non-destructive: extended_rights_tk_label is left in place; rights_object_tk_label is now a dead-table candidate. Idempotent: an assignment already present for the same object+label is skipped. Verified: all 15 assignments present in icip_tk_label, conditionForRecord now returns 'attribution' for the labelled objects where the ICIP layer previously saw nothing, allowsRecord stays true as intended, affected records still render, Unit 21/21 and Feature 231 green. This unblocks the extended_rights read/write repoint, which was blocked on re-parenting these labels
