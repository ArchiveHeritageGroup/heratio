# v1.154.716 (2026-09-04)

fix(privacy): a PII scan that could not run no longer reports a clean record, and redaction coordinates are one shape at rest. THE GUARD: PiiScanService tested four pattern scans with if (! preg_match_all(...)), and preg_match_all returns 0 when it found nothing and false when it could not run - a backtrack or recursion limit, or bad UTF-8 under the u modifier. Both are falsy, so a scan that never happened was indistinguishable from a clean one, and in this class clean is not a neutral answer: it feeds an Article 30 record and a RetentionProposal a DPO is asked to accept. Latent rather than live, and the code says so: all eight patterns were driven against adversarial input - 500k-digit runs, 200k-element alternations, long spaced digit sequences - and every one returned a clean 0. They are linear with no nested quantifier and none carries the u modifier, so there is nothing to trip today. The guard is for the patterns not yet written, and there are known to be several: ndpa and kenya_dpa are active in the registry now with no market-specific patterns at all, and a checksum-bearing national-identifier pattern is exactly the shape that can blow a limit. matchAll() compares against false explicitly, logs at error level with preg_last_error_msg, and records the pattern label; scan() resets the list and scanErrors() plus lastScanWasComplete() expose it, so a caller can tell an incomplete scan from a clean one before writing a compliance artefact. The test provokes false with a pattern that cannot compile rather than one that backtracks, because PCRE2 on PHP 8.3 optimises the classic catastrophic cases away and they return a genuine 0 - the guard tests the return value, and false is false whatever produced it. Raised by a sibling instance that had the live version of this class of defect, where a redaction filter's every failure was swallowed by a bare catch and it served the original page for months while every other signal said fine. COORDINATES: privacy_visual_redaction.coordinates held two key shapes for the same rectangle, left/top and x/y, five rows of each. v1.154.714 routed all four consumers through redactionRect() so nothing is broken, and this removes the trap rather than the symptom - a fifth consumer written next year will reach for left and be right. The migration deliberately does not call redactionRect(): a migration is a historical record and must not depend on code that can move after it has run, so the same decision is frozen inline. Only rows needing it are rewritten, so a re-run is a no-op, and a row whose JSON does not parse is left exactly as it is rather than replaced with zeros, because a zero-size rectangle is skipped by both renderers and repairing an unreadable row would silently drop a redaction. Verified on dev against a backup: ten rows on one shape, zero rectangles changed meaning. 1047 Package tests pass, up from 1044, and 286 Feature tests pass.
