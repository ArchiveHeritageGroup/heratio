# v1.154.517 (2026-08-05)

fix(#1455): DigitalObjectService::delete() no longer orphans files on disk. Root cause was the shared resolveDiskPath() stripping 'uploads/r/' (dropping the /r/ shard) so it never resolved the real layout uploads_path/r/<id>/, and delete()'s own inline logic additionally doubled 'uploads/' - so every digital-object delete removed the DB rows but left master+derivative files on disk, still fetchable under the public /uploads/ alias. Fixed resolveDiskPath() to strip only a leading 'uploads/' (keep the r/ shard) + object_id-shard fallback, additively (legacy candidates kept so redaction/other callers don't regress - the old strip had silently broken them too). delete() now uses resolveDiskPath() for file removal + fixes its empty-dir cleanup to the /r/ shard; detach() (#1447) refactored onto the same resolver so all paths agree. Verified: normal delete 3 files->0, attach/detach 3->0, resolveDiskPath resolves a real existing object (842). Note: historical deletes left an orphan backlog under uploads_path/r/* - a one-off sweep can reclaim it separately
