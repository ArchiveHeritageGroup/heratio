# v1.154.589 (2026-08-12)

feat(deploy): #1465 schedule the host-config drift check weekly, alerting via the Workbench bus. The check existed since v1.154.587 but nothing ran it, so drift would still only be found by someone thinking to look. deploy/cron/heratio-config-drift runs it Mondays at 07:00 AS ROOT and logs to /var/log/heratio-config-drift.log. Root matters: /usr/local/sbin/*.sh are mode 0750, so an unprivileged run honestly reports them 'unreadable' and skips them - scheduling it as www-data would have left the three deploy scripts unchecked, which are exactly the files whose loss prompted the issue. Weekly is deliberate rather than lazy: drift accrues over months, and the incident this guards against ran unnoticed from 2026-07-10 to 2026-08-12. NEW --notify FLAG: cron here runs MAILTO='' by house convention, so a scheduled run would otherwise report drift to nobody at all. On drift the check now drops a JSON alert into the Workbench notification inbox (/var/spool/workbench/notifications, overridable via WORKBENCH_NOTIFICATIONS_INBOX) naming the drifted files and telling the reader to decide which side is right rather than assuming the repo wins. It notifies ONLY on drift - verified a clean run creates nothing. The manifest now also includes the new cron file itself, so the checker checks its own scheduling. Verified: clean run exits 0 and raises nothing; an injected change to deploy/cron/heratio-schedule is detected, produces a correct notification payload, and exits 1; the exact cron invocation was simulated with a scrubbed environment (env -i, cron's PATH, absolute path, as root) and wrote to the log correctly. The test notification was removed from the inbox before the 15s watcher could surface it. README documents the schedule and the immediate 'sudo ./bin/check-config-drift --diff' after any edit
