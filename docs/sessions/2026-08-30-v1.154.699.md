# v1.154.699 (2026-08-30)

fix(media): a master with no derivatives could never gain any - digital_object.id was never allocated. DerivativeService updates an existing derivative row but INSERTS a new one, and the insert supplied no id. digital_object is a class-table-inheritance child of `object` and its id carries no AUTO_INCREMENT, so every insert must allocate the id from `object` first - the same rule that status.id was hardened to in #1470. Without it the insert failed with "Field 'id' doesn't have a default value" and the derivative was silently never created. The asymmetry is what hid it: a master that ALREADY had derivatives refreshed perfectly, because that path is an UPDATE, so the failure only ever struck masters that had none - exactly the ones that needed the run. The nightly ahg:regen-derivatives has been reporting ok=30 failed=4 on the demo, and all four failures were this same error. The command also threw the reason away: it collects a per-master error but only prints it under --json, which nothing scheduled passes, so the cron history carried a bare count and no cause. It now prints each failure's id and message on the plain path too. Proven on dev inside a rolled-back transaction: an existing derivative was deleted to force the insert branch, the row was recreated, and its id resolves to a real `object` row with class_name QubitDigitalObject. A full run is ok=75 failed=0. 246 Feature tests pass.
