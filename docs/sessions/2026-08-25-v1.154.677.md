# v1.154.677 (2026-08-25)

fix(ops): preserve mysqldump's stderr so the monthly rc=3 failure can finally be diagnosed - #1491. The script already INTENDED this - its comment says 'mysqldump's stderr is captured so the next genuine failure records WHY, not just an exit code' - but four defects threw it away. $ERRFILE was rm -f'd BEFORE the failure branch that would have read it, so the one artefact naming the offending table was destroyed on every failure since June; only tail -n 2 ever reached the log; attempt 2 truncated attempt 1's stderr, so two differently-failing attempts left one story; and the alert substituted a hardcoded guess, 'check /root/.my.cnf', for the actual error. Failed attempts are now APPENDED to a durable /var/log/mysql_full_dump-stderr-<date>.log at 0600, each with an rc/size/timestamp header, and the Workbench alert carries mysqldump's own words plus the path to the full text. Verified by making it fail rather than by reading it: an isolated harness with bad credentials produced both attempts preserved, a VALID JSON notification reading 'Error: mysqldump: Got error: 1045: Access denied...', and the bad dump file still correctly removed. Also corrected a comment I had written wrongly in the first pass: I claimed the existing '[ test ] && action' form would kill the script under set -euo pipefail. It does not - set -e exempts a failing command that is not the final one in an && list - and I verified that with a test script rather than leaving a confident wrong explanation in the code for the next reader. Three of the four rc=3 failures reached ~99% of a normal dump size, so this should name what happens at the END of the run.
