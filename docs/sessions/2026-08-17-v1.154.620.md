# v1.154.620 (2026-08-17)

fix(cron+data): schedules disabled in the admin were still running, and status id collisions broke record editing. CRON: registerWithLaravelSchedule iterated getDefaultSchedules() - the hardcoded array - instead of the cron_schedule TABLE, so is_enabled was honoured only by ahg:cron-run and ignored entirely by Laravel's scheduler. Every enable/disable an operator has made in the cron admin was decorative on that path, which is why three schedules disabled on 2026-08-16 carried on running and failing the next night. It now reads the table, falling back to the defaults only when it is missing or empty (a fresh install before seeding); a table whose rows are all disabled correctly schedules nothing. Verified: 93 enabled entries register, all 13 disabled ones excluded. DATA: saving a description with a publication status failed with 'Duplicate entry 914261 for key status.PRIMARY'. status is a CTI child of object - a status row's id is meant to BE an object id - but status.id is also AUTO_INCREMENT, so the twenty call sites that insert without an id silently take one from status's own counter. That had happened 417 times on heratio.org, pushing status's counter to 914643 while object's was at 914262, so every newly allocated object id collided with an existing status row and roughly 380 more failures were queued behind the one reported. A migration lifts object.AUTO_INCREMENT clear of the highest id in either table. This is a guard, not the cure - the twenty call sites still need to allocate an object row first, tracked separately
