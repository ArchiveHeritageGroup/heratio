# v1.154.730 (2026-09-11)

fix(information-object): creating a description is now one unit of work, so a failure cannot leave the nested set shifted for a record that does not exist. heratio.org logged a 1062 on 8 Sep: Duplicate entry 915856 for key slug.slug_U_1, from POST /informationobject/store. slug_U_1 is unique on OBJECT_ID rather than on the slug text, so that object already had a slug and the create tried to give it a second one. THE ERROR WAS NOT THE PROBLEM. store() ran 422 lines with no transaction and no global middleware supplying one. It shifts lft and rgt across EVERY node to the right of the parent - two table-wide updates - then inserts object, information_object, information_object_i18n and slug unguarded. A failure at the slug insert, four statements in, committed the tree shift and whatever rows had already landed. Checked rather than assumed on prod: nothing was orphaned, no information_object and no actor lacks a slug, and object 915856 does not exist - but that is luck, not design. A partially applied create here is silent, because the damage is in lft/rgt, nothing validates it on read, and a corrupt nested set makes ancestor and descendant queries wrong for records that have nothing to do with the one that failed. The write sequence is now wrapped in an explicit transaction, rolled back and rethrown rather than swallowed, so the caller still sees the failure. Proved by forcing a failure mid-create: root.rgt, the object count, the information_object count and max(rgt) all come back byte-identical, where before the fix root.rgt would have advanced by two with an orphan object row behind it. THE SLUG LOOP WAS ALSO CHECK-THEN-INSERT: while(exists) then insert proves nothing by the time the insert runs, so two creates with the same title can both find a name free and both take it. The unique index is what actually decides, so it now decides - a name collision retries the next suffix instead of failing the whole create, bounded at five attempts. A duplicate OBJECT_ID is deliberately NOT retried and is rethrown: that means the object already has a slug, and retrying under a different name would quietly give it a second one, which is the opposite of the fix. Exercised through the real controller: two records with the same title both create, taking zz-duplicate-title-probe and zz-duplicate-title-probe-1, with the tree advancing correctly; both probe records were then removed and the tree verified back to its exact prior state, with no orphaned slugs either way. 1126 Package tests pass and 286 Feature tests pass.
