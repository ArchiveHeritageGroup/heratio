# v1.154.682 (2026-08-26)

fix(ops): exclude the facet cache from the nightly dump - this is the rc=3 cause, named at last - #1491. The stderr preservation shipped in v1.154.677 caught the fifth failure and ended a four-month mystery: 'Error 1412: Table definition has changed, please retry transaction when dumping table display_facet_cache'. It was never transient. 24 Aug died at 5,192,913,641 bytes and 26 Aug at 5,192,911,527 - within 2 KB, the same point every time - and the facet-cache cron fires at 01:00:01, the same second the dump starts, rebuilding that very table. A repeated byte-identical failure size is a deterministic cause; I had assumed a transient write stall for months on no evidence. Fixed both ways. The cache table's DATA is now excluded (--ignore-table, built dynamically across the 9 databases holding it, ~240 MB saved) and its STRUCTURE appended as a second gzip member, because --ignore-table drops the CREATE TABLE as well as the rows and a restore from this file alone would otherwise lack a table the application expects - verified both directions rather than assumed. The append is deliberately NOT folded into the main pipeline: '{ a; b; } | gzip' would make PIPESTATUS[0] report gzip instead of mysqldump and silently disable the retry and the too-small-file guard, the same trap the umask handling documents. The four facet crons also move to 0,4-23, skipping 01:00-03:00 to cover the retry tail, since 24 Aug retried until 03:11. Proven on the real thing: a full run completed first attempt in 32 minutes at 9.11 GB, mode 0600, gzip integrity clean, and a scan of the finished 9.1 GB dump found 9 CREATE TABLE statements - one per database - and 0 INSERTs for the excluded table. That run also fills today's gap, since the 01:00 failure left no backup at all. Note the second attempt that night failed differently and it was self-inflicted: deploying v1.154.679 at 01:33 altered research_workspace_file mid-dump. Do not deploy during the 01:00 window.
