# v1.154.643 (2026-08-23)

fix(research,federation,acl,repository,vendor): forms that were silently RESETTING configured values on every save - #1478 class A. Eleven of the fourteen form fields that discarded input are now wired; the remaining three are unwired forms filed as #1481. TWO OF THESE WERE DATA CORRUPTION, NOT DATA LOSS, because the controllers already read the correct column names WITH DEFAULTS. Researcher types: the form posted max_advance_days / max_hours_per_day / max_materials while ResearchAdminReferenceController reads max_booking_days_advance / max_booking_hours_per_day / max_materials_per_booking with defaults 14 / 4 / 10 - so editing a researcher type reset its booking limits to those defaults regardless of what was on screen. Federation peers: the same shape, resetting harvest interval to 24 hours, clearing the default set and resetting the metadata prefix to oai_dc on every save. Five renames in total (three researcher-type, harvest_interval -> harvest_interval_hours, set_spec -> default_set) plus metadata_prefix -> default_metadata_prefix, which the scanner never saw. SECURITY CLEARANCE: the form posts nine fields and AclService::setUserClearance() wrote four. expiry_date (column expires_at), notes, vetting_authority, vetting_date and vetting_reference were all discarded - a clearance record that asks who vetted the person, when and under what reference, and keeps only the classification, is not an auditable one. setUserClearance() takes a $details array, writes only columns the installation actually has (so an instance mid-deploy keeps granting clearances instead of erroring), and the controller validates and passes all five. REPOSITORY: repository_type needed adding in FOUR places - the column, the controller's $request->only() whitelist via getAllFields(), the service update whitelist, and the service insert. Any one of the four silently dropped the value, which is a fair illustration of why this class of bug persists. VENDOR: completion_date added to extractTransactionData(), distinct from actual_return_date because work can finish before the item comes back. MULTI-TENANT: user_count was rendered on the tenant list and never computed, so every tenant showed 0 users - now a correlated subquery, so a tenant with no users still appears and no row is duplicated per user. New migration adds vetting_authority / vetting_date / vetting_reference, repository_type and completion_date, mirrored to database/core/06_form_field_columns.sql (guarded, verified loading twice against heratio_test). TWO CANDIDATES DELIBERATELY NOT ADDED, under one rule - add a column only where the field can be wired end to end in the same change: display_as_compound is meant to CHANGE how children render, not merely be stored, and authenticity_notes belongs to a view no route renders. Both are on #1481. THE SCANNER UNDERCOUNTS AND THIS PROVES IT: it sees display bindings only, so the federation form contributed 2 findings and had 3 broken fields, the clearance form contributed 3 and had 5, and the storyline form contributes 1 and has 4 plus no POST route. #1478's class-A count is a floor, not a total. Baseline 101 -> 89. Released as .643 after a concurrent .642 collision. 242 Feature tests pass; scan-blade-bindings --check clean.
