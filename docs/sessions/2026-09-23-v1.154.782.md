# v1.154.782 (2026-09-23)

feat(landing-page): WhatsApp bubble on every page, not just home and landing. It shipped in v1.154.778 included from the landing view alone, so /heritage and every other page went without it. The partial moves to theme::partials.whatsapp-bubble and the shared master layout includes it, so 1col/2col/3col pages all carry it; the landing view keeps its own include because it is a standalone fragment with no layout. Still renders nothing unless switched on in Settings > Features with an 8-15 digit number. WhatsAppBubbleTest now covers an ordinary page (/heritage) and fails without the layout include; full suite 1471 tests pass.

## Correction: two further fixes shipped in this release, added 2026-09-23

The message above describes only the WhatsApp change. Two unrelated fixes were in
the same commit, because `bin/release` runs `git add -A` and commits the whole
working tree, not the files staged by the caller. They are recorded here so the
release record matches what actually shipped. Both are in the file list below.

**CH-000175 - demo reset: drop each trigger immediately before the dump re-creates
it.** `deploy/sbin/heratio-demo-reset.sh`. The pre-restore sweep only clears the
triggers that exist when the restore starts, and on 22 and 23 September a trigger
appeared while the dump was replaying, with no artisan process running either night:
the restore died on "ERROR 1359: Trigger already exists" at line 2543 both times.
The stream now carries a `DROP TRIGGER IF EXISTS` before every `CREATE TRIGGER`, so
the restore no longer depends on identifying the writer. A failed restore also logs
each trigger with its creation time and the connections on the database, without
query text, since row values in an operator log is what CH-000135 was about. The
v1.154.780 diagnosis (a detached `runInBackground` scheduler event) was wrong; that
release's wait loop is retained because it does guard the ERROR 1050 class from 15
and 16 September. Live copy installed to `/usr/local/sbin` on 23 September 11:55.

**CH-000177 item 1 - `ahg_audit_log` stored the raw session id.**
`packages/ahg-audit-trail/src/Services/AuditLogger.php`, with a test in
`AuthAuditTest`. The raw value is the visitor's session cookie and, under the
database session driver, the `sessions` table key, so the audit viewer, its CSV
export and `audit:report` were all handing out live credentials. It is now
`hash_hmac('sha256', $sessionId, APP_KEY)`: still deterministic, so events group
into a sitting and a session used from two addresses is still visible, but it
cannot be replayed or matched back to the sessions table. It fits the existing
`varchar(128)`, so no migration. Rows written before this keep their raw ids and
cannot be rewritten, because the table is hash-chained and append-only; they age
out with the retention prune.
