# v1.154.687 (2026-08-28)

fix(repository): repository logo and banner checks read the configured uploads path, not a hardcoded one - and the IO create page stops requesting a logo it has not checked for. RepositoryBrowseService and the repository show view both decided whether to render a logo or banner by calling file_exists against a literal /usr/share/nginx/archive/uploads. That is one instance's HERATIO_UPLOADS_PATH frozen into code: correct on the demo, wrong on every other install, and wrong in BOTH directions - a logo that exists goes unshown, and an img element renders for a file that is not where the browser's request will land. The second direction was live on dev, where both logo.png and banner.png exist under the AtoM tree the code checked and neither exists under the configured root nginx actually serves, so every repository row emitted a guaranteed 404: 106 hits for logo.png and 17 for banner.png in one log. Both now resolve config('heratio.uploads_path'). Separately, the IO create page rendered its repository logo unconditionally and relied on an onerror handler to hide the broken image - which hides it visually while still firing the request and still logging the 404. It now checks the file first, keeping onerror only for the file disappearing between the check and the request. Found while triaging e2e console-error findings whose larger cause was a stale dev search index, since reindexed. Verified against the real paths on dev: the guard flips from true to false on exactly the records that were 404ing. 246 Feature tests pass.
