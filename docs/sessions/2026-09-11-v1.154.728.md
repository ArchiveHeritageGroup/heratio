## Production deployment (2026-09-11)

Released on heratio-dev, then deployed to prod (heratio) the same day.

- **Dev push.** `sudo -u www-data ./bin/release` committed and tagged v1.154.727 then v1.154.728 on heratio-dev but could not push - dev left 2 commits ahead of origin. Root cause confirmed this session: dev `origin` is HTTPS (`https://github.com/ArchiveHeritageGroup/heratio.git`) and `www-data` has no credential helper (no gh auth, no ~/.git-credentials), so an HTTPS push has nothing to authenticate with. This is not a deploy-key problem - a deploy key is never consulted over HTTPS. Pushed with root's authorized SSH key: `git push git@github.com:ArchiveHeritageGroup/heratio.git main --follow-tags`. Both commits and tags landed on origin.
- **Durable fix (applied 2026-09-11).** dev `origin` switched from HTTPS to SSH (`git@github.com:ArchiveHeritageGroup/heratio.git`). `www-data`'s existing key `/var/www/.ssh/id_ed25519` was registered as a read-write deploy key on the repo ("heratio-dev www-data"), and the key is pinned on the dev checkout via `git config core.sshCommand 'ssh -i /var/www/.ssh/id_ed25519 -o IdentitiesOnly=yes -o UserKnownHostsFile=/var/www/.ssh/known_hosts'` - repo-level rather than `~www-data/.ssh/config`, because `sudo -u www-data` keeps the caller's `$HOME` and would otherwise miss the key. Verified as www-data: `ls-remote origin` reads and `push --dry-run origin main` returns `Everything up-to-date` with no permission error. So `sudo -u www-data ./bin/release` now pushes on its own; the root SSH push is no longer needed. One deliberate consequence: because `core.sshCommand` is repo-level, remote git ops on heratio-dev authenticate only as `www-data` - other users (including root's interactive login and a Claude session running as johanpiet) get `Identity file ... not accessible: Permission denied` on that remote and must use `sudo -u www-data git ...`. This supersedes the "Known breakage (2026-07-05)" note in the global dev-first workflow rule.
- **Prod deploy.** `sudo /usr/local/sbin/heratio-deploy.sh --check` then the live run took prod from 1.154.726 to 1.154.728 (HEAD c9242d8b8, in sync with origin). Post-deploy guard `bin/deploy-check` passed: vendor in sync with composer.lock, composer audit clean (no high/critical), app boots, mail sink ok. The one SKIP (recent-inbound-mail) is unrelated - it needs `DATABASE_URL` in `api/.env`, absent for CLI runs.
- **Cron verified on the deployed version.** `/etc/cron.d/heratio-config-drift` runs `bin/check-config-drift --notify` as root Mondays 07:00, logging to `/var/log/heratio-config-drift.log`. Confirmed the deployed prod copy is the new version (chmod 644, ahg-report-error wiring, CONFIG_DRIFT_STATE, stable --fault keys), `bash -n` clean, side effects gated behind `--notify`. Full root run - exactly as cron invokes it, minus the alert - reported `no drift (19 compared, 1 not installed here)` with no unreadable gaps and no trap/error output. The demo-script drift that stood on the v1.154.726 (Sep 8) run was reconciled by this deploy, so the next Monday `--notify` run will simply log `no drift` and stay quiet.
