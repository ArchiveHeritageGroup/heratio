# v1.154.579 (2026-08-12)

fix(rights): #1464 consolidate rights_embargo into embargo - one embargo table, one expiry path. The two embargo tables were split-brain across write, display AND expiry: embargo is written by ahg-information-object-manage and ahg-rights-holder-manage, read by EVERY record show page (io-manage, library, dam, museum), the core sidebar and the search rights-indicator, and its expiry command ahg:embargo-process IS scheduled; rights_embargo was written by ahg-extended-rights (EmbargoService) and ahg-scan (RightsEnforcementService), read by one context menu, and its expiry command embargo:process is a SECOND command that was never scheduled. So an embargo created through the second pair did not display on any record page and would never auto-lift - failing in both directions: material that looks unrestricted when it is not, and material that stays restricted past its release date. embargo is authoritative: it is already the display and enforcement path and carries the fields display needs (is_active, public_message, is_perpetual). MIGRATION 2026_08_12_090000 folds in the seven workflow columns rights_embargo had and embargo lacked (auto_release, review_date, review_interval_months, last_reviewed_at, last_reviewed_by, notification_sent, notify_emails - all additive) then MERGES rather than copies: an object can already carry the same embargo in both tables recorded through the two paths, so a rights_embargo row whose object already has an embargo of the same type only enriches that row, and only genuinely absent ones are inserted. On dev that merged the one row into the existing metadata_only embargo for object 1264537 with no duplicate created. REPOINTED all six writer/reader sites: EmbargoService (26 refs - the rights_embargo_i18n joins drop out entirely since embargo carries reason/notes as direct columns), EmbargoNotificationService, both extended-rights commands, ahg-scan RightsEnforcementService (now also sets is_active), and the context-menu blade. Fixed the transposed column name on the way (rights_embargo.notify_before_days is embargo.notify_days_before) and aligned EmbargoService's insert with the authoritative writer's semantics - embargo.reason is FREE TEXT, not the enum rights_embargo used, so the operator's wording is kept and the enum is retained only for the audit entry. rights_embargo is deliberately NOT dropped: the writers move in this release, but dropping an access-control table on the same deploy that changes its writers leaves no fallback, so removal is a follow-up once this is proven in the field. The unscheduled embargo:process is annotated as the manual/advanced variant so nobody schedules a second processor against the now-shared table. Verified: EmbargoService retrieval, create (free-text reason, notes, is_active, auto_release all correct), both commands run clean against the single table, embargo:report sees the merged row, show pages render, Unit 21/21 and Feature 231 green
