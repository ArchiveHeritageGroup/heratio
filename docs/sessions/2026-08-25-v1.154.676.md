# v1.154.676 (2026-08-25)

feat(ops): live VM image backups to the NAS - #1486. Until today no VM image was backed up anywhere: no libvirt snapshots, no ZFS snapshots over the NFS mount, no copy of any qcow2. The databases were dumped nightly so the archives were safe, but the guest OS and application layer of all 8 VMs had no restore point at all - which is what made yesterday's hard reset of the atom VM a gamble rather than a routine action. deploy/bin/vm-backup.sh uses libvirt's push-mode backup API (virsh backup-begin, libvirt 10.0.0), so guests keep RUNNING throughout: verified on two domains, heratio-dev 7.5 GB in 5 min and ahgerp 6.1 GB in 5 min, qemu-img check clean on both, neither left the running state and all 8 domains up afterwards. WEEKLY ROTATION rather than nightly-everything because the measurements forbid it - throughput to the NAS is ~25 MB/s against ~1.6 TB of images, so a nightly full sweep would take ~17 hours and never finish before the working day. Mon atom (192 GB), Tue archivematica (300 GB), Wed rari-dev + atom28 + atom210 (65 GB), Thu heratio-dev + ahgerp (25 GB), Sat Mogalakwena - 1 TB and ~11 hours, which is why it gets the weekend - with Fri and Sun spare for a retry after a failure. Domain XML for EVERY domain is dumped on every run, including spare nights: tiny, and without it you cannot recreate a VM definition even holding the disk. Four things are deliberate and commented as such - no timeout on the block-job wait, because killing a merely-slow 11-hour backup leaves you with nothing; qemu-img check on every output, because a file of the right size that qemu cannot open is not a backup; retention pruning skipped for any domain that failed, so older good copies survive a bad run, matching mysql_full_dump.sh; and a 2 TB free-space guard before it starts. Failures ring the Workbench bell. Registered in bin/check-config-drift alongside mysql_full_dump.sh so the host copy and the repo copy cannot silently diverge.
