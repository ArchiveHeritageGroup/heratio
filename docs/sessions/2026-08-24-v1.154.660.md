# v1.154.660 (2026-08-24)

feat(deploy-check): fail the check if an instance would send real mail. A fourth check that asks the RUNNING application where mail would go - config('mail.default') and the resolved smtp host - rather than reading .env. It exists because .env lied for months: a QA crawler filled heratio-dev's contact form 7 times on 2026-08-24 and sent 14 real messages through Gmail while .env said MAIL_MAILER=log and everyone believed it. SINK-BY-DEFAULT. A sink is log, array, null, or smtp pointed at 127.0.0.1 / localhost / ::1 / mailpit / mailhog - a local Mailpit is still a sink even though the mailer is smtp. Anything else FAILS, printing the resolved mailer, its destination, what .env claims for contrast, and - only when the two disagree, which is the bug class itself - that something overrides .env at boot. MAIL_ALLOW_SEND=1 in .env declares sending deliberate and turns the failure into a pass, so an instance that legitimately sends says so once instead of the check crying wolf at it forever. Hard failure rather than a warning because sending mail and NOT sending mail look identical from outside: a broken page announces itself on the next request, a re-armed mailer announces itself in somebody's inbox days later, to a person who was not watching. Detection asymmetry is a better reason to guard something than probability is. THE sendmail BRANCH IS NAMED EXPLICITLY because it is the trap that nearly caught this fix: heratio.org's .env said MAIL_MAILER=sendmail, /usr/sbin/sendmail on this host is a symlink to msmtp, and /etc/msmtprc has a default account relaying to the same Gmail. Disabling the DB override alone would have rerouted mail rather than stopping it, and looked like a fix. The check resolves the symlink and says so. WHY ASKING THE APP IS THE ONLY CORRECT METHOD: heratio-dev turns out to have THREE layers deciding the mailer, and the last one wins - .env, then email_setting via AppServiceProvider, then mva_mail_setting via the dev-only ahg-mva-claims provider, which currently pins dev to log. No file tells you the truth; only the resolved value does. That is also why .env said sendmail during testing while the app still resolved log. VERIFIED: the nine-case decision table exercised directly (log, array, smtp-to-local-sink, smtp-to-mailpit, smtp-to-Gmail, smtp-to-Gmail-declared, sendmail, sendmail-declared, empty-input), and end to end against a live instance in both directions - FAIL with sendmail resolving to /usr/bin/msmtp, OK after restoring the sink - using a throwaway copy of the script so no instance ran unreleased code. All three instances currently pass: dev, heratio.org and sasa all resolve to log.
