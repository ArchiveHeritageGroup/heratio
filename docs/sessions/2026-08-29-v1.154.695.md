# v1.154.695 (2026-08-29)

fix(cron): a successful scheduled command was recorded as failed - #1498. CronSchedulerService truncated command output with strlen()/substr(), which count BYTES while the comment above them says chars. Cutting at byte -5000 leaves a dangling UTF-8 continuation byte, MySQL rejects the write to last_run_output with error 1366, and the exception propagates out of the run so ahg:cron-run exits 1 - reporting a command that had already completed as a failure. This is the inverse of the failure we usually chase: not a failure reported as success, but a success reported as failure, and it destroys the signal just as thoroughly. It is why the demo currently shows a red banner reading 'Scheduled command ahg:cron-run failed with exit code [1]'. Progress bars make it certain rather than occasional: they emit long runs of U+2593 DARK SHADE, three bytes each, and 5000 is not divisible by three, so a tail of block characters is cut mid-character EVERY time - measured at all three alignments, the byte cut produced invalid UTF-8 in all three and mb_substr in none. Five scheduled commands render a progress bar. Fixed three ways. The truncation uses mb_strlen/mb_substr so it keeps 5000 characters as the comment always claimed. Progress output is collapsed to the final state of each carriage-return-rewritten line before storage, because thousands of block glyphs nobody will read otherwise crowd the tail of the log - the part worth keeping - out of the 5000 retained. And the status write is wrapped so that recording an outcome can never change it: on failure it logs, retries without the output field since that is the only one big or oddly encoded enough to be the cause, and leaves the run's real result intact. 246 Feature tests pass.
