# v1.154.680 (2026-08-26)

feat(research): fetch external documents on the queue instead of the request - #1492. The fetch was synchronous, so a slow source held a php-fpm worker open for up to the 30s HTTP timeout against a 100 MB ceiling while the researcher watched a spinner. ResearchSourceFetchJob now does the work; the controller dispatches and returns immediately. THE URL IS CHECKED TWICE, deliberately: synchronously in the controller so an unfetchable URL is refused at the form rather than by a notification minutes later, and again inside the job before it downloads, because DNS can change between dispatch and execution and the second check is the one that is actually load-bearing. The first is for the person, the second is for safety. A REFUSAL IS AN ANSWER, NOT A FAULT: an SSRF rejection, an oversized document or a disallowed type notify the researcher and stop - they are not retried and do not land in failed_jobs, because retrying re-proves the same refusal and a job in that table reads as an outage to whoever inspects it. Only genuine exceptions reach failed(). Two attempts, not three: a fetch is not idempotent and a retry after a partial success would duplicate the file. Only scalars are serialised onto the queue - the service, SSRF guard and quota engine are resolved inside handle(), since a payload sits in the database until a worker takes it and freezing dependencies at dispatch time is how a queued job ends up running yesterday's code. Completion and failure both write a research_notification linking back to the workspace. Verified against a real worker: example.com fetched, file and provenance recorded, researcher notified, queue drained, zero failed jobs; and a blocked metadata URL notified with the true reason while writing no file and queueing no retry. 238 Feature tests pass, including a new one pinning that a refusal does not fail the job.
