# v1.154.661 (2026-08-24)

feat(deploy-check): step 5 - report recent inbound mail before a release. Checks 1-4 ask whether the thing you are about to deploy is sound. Step 5 asks whether somebody has already told us it is not. On 2026-08-24 four fault reports from a user arrived over about two hours while unrelated releases were going out, and the first was read only after the third had been fixed. IT NEVER BLOCKS. Step 5 sets no failure flag, and the whole point is that it cannot: a waiting report might describe the very thing you are shipping, or might be unrelated, and that is a judgement for the person deploying rather than for a script. A mail server having a bad afternoon must not be able to stop a release. It is wrapped in timeout 45 because it makes a network call, and this script must never be able to hang a deploy. Implementation is deliberately a CALL, not a copy: it invokes ahg-archive's bin/mail-check.cjs, which reads the mailbox through the Workbench's own Graph client - the client that owns the OAuth refresh and the encrypted token. Duplicating it here would mean duplicating the key handling. The account is resolved by UPN, so the script is independent of which repo calls it; my first assessment that this would need a separate implementation for Heratio because Heratio sends via Gmail was wrong, and is corrected here - the check never touches the sending path. Being a cross-repo dependency it degrades rather than breaks: absent script, absent node, or SKIP_MAIL_CHECK=1 all skip cleanly, and MAIL_CHECK_BIN and MAIL_CHECK_HOURS override the defaults. VERIFIED WORKING, AND THEN VERIFIED DEGRADING. On first run it listed 28 messages from the last 24h and flagged 4 as fault reports, which is what prompted the investigation it was built for. Twenty-five minutes later the same call returns SKIP: the mailbox OAuth grant was revoked at 15:20:47 SAST (AADSTS50173, TokensValidFrom stamped when an account password is changed or reset), so the check is blind until the mailbox is re-authenticated in Workbench. That is the designed behaviour - it reports the skip and passes - but it is worth recording that the earlier successful run was served by a CACHED access token and looked perfectly healthy while the underlying credential was already dead. A stale credential that reports success until something forces a refresh is the same shape as the other seven instances this estate hit today, and this one was caught only because someone asked for the message bodies, which forced the refresh.
