# v1.154.711 (2026-09-03)

fix(release,hooks): the diff-marker gate no longer rejects prompt templates, and a refused commit no longer publishes to KM. GATE 3 scans every staged source file for three or more consecutive lines opening with + or -, the tell of a unified diff pasted as file content. A markdown bullet list has exactly that shape, so any file carrying a bullet list at column 1 inside a heredoc was uncommittable from the day the gate shipped. Two were, and only one was known: ComplianceAutopilotService, whose DPIA and retention prompts had to be indented by one space at v1.154.710 to get that release through, and AnnexIvCommand, whose Annex IV markdown template has never once been committable and surfaced only by sweeping all 10,184 tracked source files with the gate's own awk. The gate now tracks heredoc and nowdoc bodies and skips them. That is the right boundary rather than a convenient one: a heredoc is where prose legitimately lives in this codebase, and the cost of the exemption is that a diff pasted inside a string literal is no longer caught, which cannot fail to parse or swallow a closing brace and so is not the failure this gate exists to stop. The workaround indentation is reverted, whitespace only, 13 lines, proven by diffing both revisions with leading whitespace stripped. Verified end to end against the real hook in a scratch repo rather than against the awk alone: both prompt files commit, a pasted diff is still refused, a bullet list outside a heredoc is still refused, and the repo-wide sweep now flags nothing where it flagged one. Left uncovered and stated plainly: a JS template literal holding the same bullet list still trips the gate, latent rather than active since no such file exists. KM SPOOL: bin/release copied the session log into /var/spool/km-ingest BEFORE git commit, so a commit the hook refused had already published a release record for a release that does not exist. v1.154.710 did precisely that and left an orphan spool file behind, so KM carried the release before the repo did. The drop now sits below commit and tag, and deliberately not below push, for the same reason the unlock cleanup sits where it does: dev's push always fails and set -e would exit before KM ever heard about a release that is locally complete.
