# v1.154.678 (2026-08-26)

fix(ahg-ric): SPARQL writes were landing in the RiC-O ontology dataset, not the data dataset - #1487. fuseki_update_endpoint is an ABSOLUTE url stored in ahg_settings that silently overrides the value derived from fuseki_endpoint, so read and write targets drift apart and nothing fails - Fuseki accepts an UPDATE against any dataset it serves. Measured: /ric holds 648 rico:Record, /openric-model holds 19,992 triples and ZERO Records because it is the ontology. heratio-dev read /ric and wrote to /openric-model; the demo did BOTH against /openric-model, so its RiC Explorer had nothing to show - the same regression recorded as having silently reverted once before. SparqlUpdateService now compares the dataset segment of both endpoints and on mismatch uses the one derived from the READ endpoint, which is authoritative because it is the dataset the application demonstrably reads back from, logging a warning that names the exact setting to correct. THE REAL BUG was that FusekiSyncService resolved endpoint, username, password and timeout a SECOND time for its queued path and dispatched FusekiSyncJob with them - so with fuseki_queue_enabled=1, the default on every instance and the active path, the guard would have been bypassed entirely. That duplicate lookup is gone; SparqlUpdateService is now the single place fuseki_update_endpoint is resolved. Two copies of one lookup is how they drift, which this session has seen four times in the loan-rule query alone. Stored settings corrected on dev and the demo as well as guarded in code, since the guard masks the wrong value rather than repairing it. 64 ahg-ric package tests and 231 Feature tests pass.
