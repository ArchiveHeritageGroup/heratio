# v1.154.622 (2026-08-17)

fix(#1470): every status write now allocates an object id - the cure, not the guard. status is a class-table-inheritance child of object, so a status row's id must BE the id of an object row with class_name QubitStatus. But status.id is also AUTO_INCREMENT, so twenty call sites that omitted it silently drew from status's own counter instead - 417 times on heratio.org, which pushed that counter past object's and made every newly allocated object id collide with an existing status row, breaking description saves with 'Duplicate entry for key status.PRIMARY'. v1.154.620 lifted object's counter clear of the range, which stopped the failures but only bought distance; the id spaces would have drifted together again. New AhgCore Support StatusRow owns the allocation: allocateId() for callers building their own row, set() to replace a status, put() as a true drop-in for the updateOrInsert shape (it UPDATES in place, keeping the existing id, and allocates only when inserting), and ensure() for write-if-absent. All twenty sites converted - eleven plain inserts across gallery, IO service and controller, digital objects, the v2 API, DAM, data migration, RecordCreationService, SectorSampleService and the CSV importer; seven updateOrInsert sites across the DACS/RiC/DC/MODS/RAD standard controllers, archaeology and AclService; the scale-corpus bulk seeder; and two test fixtures that were modelling the bug. Verified: set() produces a genuine QubitStatus object row, put() preserves the id on update, one row per object/type, and the 11 tests in the two affected suites pass. The 275 historical orphaned status ids are untouched - they work today and are noted on the issue. status.id could now stop being AUTO_INCREMENT so a future omission fails loudly, but that is a separate change and not one to make in the same release
