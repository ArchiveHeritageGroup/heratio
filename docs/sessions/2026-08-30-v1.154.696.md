# v1.154.696 (2026-08-30)

fix(cron): a crashed run disabled its schedule permanently - reclaim stale locks. getDueSchedules() excluded any row whose last_run_status is 'running'. That status is set before the command starts and cleared only when it finishes, so a run that dies without writing a terminal status - a crash, an OOM kill, a host or deploy restart mid-run, a timeout - left the row marked running forever and the query never returned it again. The schedule was then silently disabled for good: no error, no failure count, no alert beyond a missed-run record nobody was reading. On the demo this had killed ahg:search-update for 12 hours and ahg:qdrant-image-index for FOURTEEN DAYS, at 343 times its own 60-minute timeout, and the only visible symptom was a job that had quietly stopped happening. A row still marked running past its own timeout cannot be a live run, and every row already carries timeout_minutes to measure against - the scheduler simply never used it. Stale rows are now returned as due and reclaimed, marked failed with the reason written into last_run_output and a warning logged, so the history shows an abandoned run rather than an unexplained silence. The comparison deliberately uses the APP clock rather than MySQL NOW(). last_run_at is written by PHP in the app timezone (UTC) while MySQL NOW() returns the server timezone (SAST), two hours apart - my first version used NOW() and a boundary test caught it reclaiming a lock zero minutes old, which would have killed every genuinely running job on the first pass. Tested at five ages against a 60-minute timeout: 0, 30 and 59 minutes are left alone and stay not-due; 61 and 600 minutes are reclaimed and become due. 246 Feature tests pass.
