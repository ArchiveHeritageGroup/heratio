# v1.154.724 (2026-09-08)

chore(repo): ignore the two commercially sensitive reference documents here, so no instance needs a hand-edited .gitignore. The 1.154.709 to 1.154.723 deploy aborted on prod with 'Your local changes to the following files would be overwritten by merge: .gitignore'. The cause was not a conflict of content: the incoming change adds graphify-out/ and the production copy adds two ignore lines, and the two are entirely compatible. It was skip-worktree. The production instance held its extra lines in place with git update-index --skip-worktree, which makes git refuse to touch the file at all, so ANY incoming change to .gitignore aborts the pull - and it also hides the difference, so git diff reports nothing and git status shows a file with no visible changes blocking a merge. THE OBVIOUS UNBLOCK WOULD HAVE BEEN A DISCLOSURE. Taking the repository's version, by checkout or by letting the merge win, drops those lines. Both documents exist on the production instance and are untracked ONLY because of them, so they would have become untracked-but-not-ignored and the next release's git add -A would have staged and pushed commercial material to a PUBLIC repository, silently and with no error anywhere. Verified before changing anything: neither file has ever been committed, on any branch, so nothing is already exposed and the ignore has been doing its job. Ignoring them in the repository removes the per-instance deviation entirely - the production copy can go back to matching, skip-worktree can be cleared, and the next .gitignore change will not block a deploy. The paths are named here, which the contents never are; that trade was made deliberately, because a protection that has to be re-applied by hand on every instance is a protection that eventually is not. Confirmed effective rather than assumed: a file created at one of those paths is invisible to git status, and git check-ignore names the rule. No application code changed.
