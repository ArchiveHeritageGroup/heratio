# v1.154.732 (2026-09-11)

docs(sessions): adopt the v1.154.728 deployment record that was written on the live instance and never committed. The prod deploy aborted with 'live has uncommitted tracked changes: M docs/sessions/2026-09-11-v1.154.728.md' - correct behaviour, and the reason it mattered is what the file contains. Another session appended a nine-line deployment record directly to the copy on heratio: the dev push diagnosis, the durable fix applied that day, the prod deploy result and a cron verification. Discarding it with git checkout would have cleared the abort and thrown the write-up away; it exists nowhere else. Adopted into the repository instead, byte for byte, so the live copy and the tracked copy agree and the working tree can go clean without losing anything - the same reasoning as adopting the live demo-reset and demo-snapshot scripts at v1.154.723. Two things in it are worth surfacing rather than leaving buried in a session log. First, dev's origin was moved from HTTPS to SSH deliberately, with www-data's key registered as a read-write deploy key and core.sshCommand pinned at REPOSITORY level so that sudo -u www-data ./bin/release can push on its own; the root SSH push is no longer needed and this supersedes the 'Known breakage (2026-07-05)' note in the global dev-first rule. Second, and stated there as a deliberate consequence: because core.sshCommand is repo-level, remote git operations on heratio-dev authenticate only as www-data, so every other user - root's interactive login and a Claude session running as johanpiet included - is refused on that remote and must use sudo -u www-data. That explains the 'Host key verification failed' that ended bin/release at the push step for v1.154.730 and v1.154.731: not a broken remote, but the documented behaviour of the new configuration meeting the wrong user. Both releases were pushed over HTTPS by hand and are on origin; the commits and tags were never at risk. No application code changed.
