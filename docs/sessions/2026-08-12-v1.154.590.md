# v1.154.590 (2026-08-12)

fix(deploy): #1465 heratio-deploy.sh health-checked the wrong domain, and checked it too late to matter. THE URL: it hit https://heratio.theahg.co.za/, which is a 301 redirect and never served this docroot - /usr/share/nginx/heratio/public is served by heratio.org.conf (server_name heratio.org www.heratio.org). So every deploy's closing 'live HTTP 301' line was confirming a redirect existed, not that the app was up. Now checks https://heratio.org/, which returns 200. THE ORDERING, which mattered more: the health check ran AFTER the demo-baseline rebase, so a broken deploy was snapshotted as the golden state the 02:00 reset restores to - baking the breakage in and re-applying it nightly, with the check reporting the failure only once it was already too late to prevent. The check now runs BEFORE the rebase and gates it: on a non-200 the baseline is left describing the previous release and the script says so loudly. That produces a safe cascade rather than a silent one - unhealthy deploy -> baseline not rebased -> the reset's version guard (v1.154.583) sees a stale baseline and refuses -> the demo keeps serving current code instead of being reset into a known-bad state, and the operator is told to run heratio-demo-snapshot.sh once the app is healthy. Deliberately does NOT exit non-zero: migrations have already run and php-fpm has already reloaded by that point, so the deploy genuinely did happen and pretending otherwise would be misleading; the loud warning plus the withheld baseline is the honest signal. Verified both branches by extracting the block and running it against a real 200 and a forced 404. Repo copy synced in the same change and confirmed by bin/check-config-drift, so the mirror stays honest; README's 'Known issue' section is replaced by a 'Deploy ordering that matters' section explaining why the sequence is not arbitrary
