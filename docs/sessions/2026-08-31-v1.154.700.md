# v1.154.700 (2026-08-31)

feat(core): render QR codes locally - three labels were calling a third-party service and a fourth was already dead. Every QR in the platform came from outside it: ahg-spectrum's museum label, ahg-label's single and batch label views all fetched from api.qrserver.com, and the v2 identifier API returned an img tag pointing at chart.googleapis.com, which Google retired - that field advertised a QR and served a 404. bacon/bacon-qr-code was already a dependency and already used server-side for two-factor setup; the label code simply never used it. Two things made the external calls wrong beyond the broken one. A label print told an outside service what the institution holds - the record URL, and so the identifier of a possibly restricted or culturally sensitive item, left the building on every render, and nobody chose that. And labels stopped working without internet access, so a reading room, a store room or an air-gapped install could not print at all. New AhgCore\\Services\\QrCodeService renders through the bundled library and returns null rather than throwing when a payload is empty or over length, because a label that prints without its QR is far better than a page that 500s. It embeds a data URI rather than linking, so the code survives being saved, emailed or printed to PDF and needs no second request at print time - which is precisely when a label is most likely to be somewhere with no network. The identifier API now returns real SVG markup in its svg key rather than an img tag, plus a data_uri alongside. Verified on the running instance: the museum label returns 200 with one inline SVG QR and zero external requests, and batch print returns 200 with one per label and zero external requests. 246 Feature tests pass.
