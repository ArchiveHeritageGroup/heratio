# v1.154.693 (2026-08-29)

fix(release): never release onto a tag that already exists. bin/release computed the next version from version.json alone, which is only correct while version.json and the tags agree. They come apart in two ordinary situations: another session releases concurrently, or a release's own version.json bump fails to persist - which is what happens when a root-run git leaves the file root-owned and the next www-data release cannot write it. Either way the file lags the tags, the next patch computes a number already in use, and the push is rejected AFTER the commit and tag are made, leaving a half-finished release to unpick by hand. That happened twice on 2026-08-29: a parallel session took v1.154.688 while its own version.json still said 687, so the next release computed 688 and collided, then collided again on the retry. Recovery needed a reset to the remote head and a hand-edit of version.json, which is a file the project rules say only bin/release may touch. The script now learns about tags created elsewhere and steps over any that are taken, reporting that it did so and pointing at the likely cause. The fetch is deliberately best effort and never fatal: dev cannot reach origin over HTTPS, so it tries origin, then an SSH URL derived from the origin remote, and continues regardless - a release must not be blocked by a network failure. Verified against the real tag list: a version.json six versions behind now lands on the first free tag rather than the first taken one, the SSH fallback recovers a tag that exists only on the remote (origin fails silently as expected on dev), and an already-correct version.json is passed through untouched.
