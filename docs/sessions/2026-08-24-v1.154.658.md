# v1.154.658 (2026-08-24)

fix(help): five user-manual images 404'd on every help page - an AtoM /plugins/ path that Heratio does not serve. docs/help/user-manual.md and docs/USER_MANUAL.md both embedded <img src="/plugins/ahgHelpPlugin/images/...">, the path convention of the AtoM plugin the help system was migrated from. Heratio is Laravel and serves no /plugins/ docroot, and the image files were never carried across the migration, so all five 404'd on every page that embedded them - 19 pages each, 95 failed requests per full crawl of the help corpus. The originals were still present in the old AtoM install on this host and are restored to public/images/help/, which establishes the convention: these were the ONLY <img> references in the entire 482-article help corpus, so there was no existing location to follow. Both manuals rewritten and help re-ingested. Verified: the live /help/article/user-manual page carries zero references to the old path, all five images return 200, and a sweep of every markup-referenced asset on that page returns no non-200. A NOTE ON WHAT THIS IS NOT. This was found while investigating a QA report of 819 failures on the Help target. It is worth recording what those 819 actually were, because the number is misleading in three separate ways. Of 1603 404s in that crawl window, 1442 were /uploads/r/... digital-object derivatives and are not a defect at all - the instance was serving the production database while running on dev's filesystem, so every image path pointed at a derivative that exists on prod's disk and not on dev's; that population disappears once the instance reads its own database again. 95 were these five images. I also reported ~16 missing hashed webpack assets and 6 quote-mangled URLs in the theme bundle, and BOTH were artefacts of my own extraction rather than defects: the six sit inside a jQuery-UI ThemeRoller query string embedded in the CSS and are never requested, and the sixteen, while genuinely absent from disk, are referenced only by selectors that never match on these pages - the access log shows every dist/ asset request in the window returning 200, and the only requests for the missing hashes were my own curl probes. They are left alone deliberately. Restoring them by inference was attempted and abandoned: the webpack filename hash does not match a truncated md5 of the candidate source files, so no mapping could be proven, and jstree and slick bake sprite coordinates into background-position, where a version mismatch would silently shift every icon rather than fail loudly. An unprovable mapping is the same mistake as a fuzzy rename.
