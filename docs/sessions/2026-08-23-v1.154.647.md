# v1.154.647 (2026-08-23)

fix(ai,privacy): NER entities are finally attributable to the run that produced them - #1479; and 'no score' stops rendering as 0% - #1480. #1479 WAS ENTIRELY REAL. createAccessPoints() opened a ledger row and closed it with a count, but neither of the two insert sites - createAccessPointsInner() and createAccessPointsFromDetailed() - ever set ahg_ner_entity.extraction_id. So every ledger row asserted a count of entities that nothing could reach from it. #1472 wrote a backfill to adopt the historical orphans; the writer went on making new ones, which is a fix to the data rather than to the cause. Verified on current main before the fix: 4 ledger rows claiming 16 entities, all 16 with extraction_id NULL. Now ONE private insertNerEntity() writer serves both paths - two hand-maintained copies of a single insert is exactly how they drifted, the same shape as the three loan-rule lookups in v1.154.634 and the two CCO whitelists in v1.154.639 - and the ledger id is threaded down from createAccessPoints(). Guarded on Schema::hasColumn so an instance whose #1472 migration has not run still writes entities instead of erroring. NerExtractionLedger::complete() now compares the count it is about to record against the entities actually carrying that extraction_id and logs a warning when they disagree; the #1472 migration already reconciles after a backfill, and doing the same at WRITE time is what would have caught this on the first run. Warn only - a logging check must never fail an extraction that otherwise succeeded. Verified end to end: a fresh run over four records reconciles 4/4, 4/4, 5/5, 3/3 with ZERO orphans, and the guard demonstrably fires when a row claims 3 with 0 linked. #1480 I FILED PARTLY WRONG AND HAVE CORRECTED ON THE ISSUE. The writer does not hardcode a confidence and never did: the legacy path writes null because it genuinely has no per-entity score (its own comment says 'honest: we have no per-entity score') and the entities_v2 path says 'a real float OR null. Never the hardcoded 1.0'. The 2,003 rows at exactly 1.0 are HISTORICAL - last written 2026-05-05, while every row since 2026-08-06 is null - so my '96% are 1.0' was a statement about legacy data presented as current behaviour. The real defect was one line in pii-review.blade.php: round($entity->confidence * 100) turns NULL into 0, and 0 is below the 60 threshold so it rendered in text-danger red. 'We have no measurement' therefore displayed as 'the model is confident this is wrong' - inverted meaning, and a figure where there is no figure, which is the #1478 family again. The queue now renders 'Not scored' in muted text with a tooltip saying it is not the same as a score of zero. NOT DONE, deliberately: the 2,003 legacy 1.0 rows are left alone rather than backfilled to null, because that would destroy data on an inference about what changed on 5 May - the dates are evidence, not proof. 242 Feature tests pass; scan-blade-bindings --check clean.
