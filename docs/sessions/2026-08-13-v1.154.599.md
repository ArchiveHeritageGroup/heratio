# v1.154.599 (2026-08-13)

fix(deploy): #1465 heratio-deploy.sh restarts php-fpm instead of reloading it. These pools run opcache.validate_timestamps=0, so a worker never re-stats a PHP file once compiled and a graceful reload leaves the PREVIOUS release in the shared opcache while the site carries on serving it. The failure is deceptive - php artisan from the CLI reads the new files and reports everything healthy while the browser runs old code - and it is what produced the spurious 405 on the demo on 2026-07-31, after which every deploy needed a manual restart to actually land. The trade is a brief drop of in-flight requests rather than a graceful drain, which is right on a demo host: a deploy that silently does not take effect is worse. Because a restart is not instantaneous the health check now retries for ~15s and breaks on the first 200, otherwise a single immediate check could catch the restart gap, fail a good deploy and skip the baseline rebase. Compiled manifests (packages.php, services.php, config.php, events.php, routes-*.php) are removed just before the restart, since a newly registered provider lands in those and a stale one is the classic post-deploy 500. Repo copy installed to /usr/local/sbin and drift-checked
